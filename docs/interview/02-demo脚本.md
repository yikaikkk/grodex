# Grodex 面试 Demo 脚本（15 分钟版）

> 原则：**每个环节有"如果失败"的兜底**。demo 的目标不是炫技，是不翻车。
> 面试前必做：release 构建 + 全程预演 2 遍 + 备好一个已跑通的 session_id。

---

## 面试前检查清单（提前一天）

```bash
# 1. release 构建（demo 用 release，不是 debug——不然大文件读取会肉眼可见地卡）
cargo build --release

# 2. 预演：完整走一遍下方脚本，确认每个命令的输出和你预期一致

# 3. 权限预设：把只读工具设为 allow，避免现场弹审批打断节奏
#    （config 里 read_file/edit 相关 policy 调宽松；把"审批演示"留给专门的环节）

# 4. 准备一个"已跑通的会话"作为崩溃恢复演示素材：
#    开一个 session 跑 2-3 轮工具调用，记录 session_id，别删 journal

# 5. 网络确认：模型 API 可达；把 API 连接的超时调宽松
```

## Demo 流程

### 环节 0：开场（0:00-1:00）
> "这是我自己用 Rust 写的 AI 编程代理。这个对话就跑在它自己的 serve 进程里。
> 我讲 4 个东西：它怎么工作、崩了怎么恢复、怎么防危险操作、怎么验证正确性。"

### 环节 1：让它干活（1:00-4:00）——证明"真的能用"
```bash
./target/release/grodex run --cwd <一个小项目目录>
# 提示词：阅读这个项目的结构，告诉我它做什么，然后指出一个可以改进的地方
```
- 预期：模型读文件 → 分析 → 给出结论。**用小项目**（<200 文件，避开 O(n) read 的坑）。
- 顺带可秀：TUI 里的 token 缓存百分比（prompt caching 生效）。
- 兜底：如果模型 API 慢，直接切到下一环节，说"日常使用就是这样"。

### 环节 2：崩溃恢复（4:00-7:00）——核心卖点，必演
```bash
# 预先准备：一个跑了一半的 session（面试前录好）
# 现场演示两步：
./target/release/grodex inspect <sid>        # 1. 展示 journal：一列事件(seq/类型/时间戳)
./target/release/grodex resume <sid>         # 2. 恢复到中断点，模型"记得"之前干了什么
```
- 讲解词："每个动作先写 journal 再执行，所以 kill 不丢数据。resume 就是重放 journal。"
- 进阶（时间够且已预演）：现场 `kill -9` serve 进程 → 重启 → `resume` → 问模型"你刚才在干什么" → 它答得上来。**这一段是全场高光，值得留 2 分钟。**
- 兜底：kill -9 那段如果 journal 重放异常，立刻说"看 inspect 的输出，事件是完整的"，然后切下一环节，别在现场修。

### 环节 3：安全（7:00-10:00）——证明"不是玩具"
```bash
# 3a. 审批：调一个高风险工具（如 exec 写系统路径），现场弹出审批工单
#     展示 Allow / Narrow / Deny 三选一，narrow 之后"只这一次"生效
# 3b. 沙箱：配置 sandbox 后让模型尝试读系统目录（如 /etc/passwd），
#     展示内核拒绝（EPERM），不是 chroot 模拟，是 macOS Seatbelt 强制
```
- 讲解词："权限分两层：策略层（谁来调用）和沙箱层（内核强制能碰什么）。fail-closed：没声明的一律拒绝。"
- 兜底：沙箱演示如果被系统提示干扰，口头补一句"核心是 fail-closed 语义 + 集成测试验证"，不硬演。

### 环节 4：可验证性（10:00-13:00）——证明"不是写死 demo"
```bash
./target/release/grodex dump <sid>           # 结构化导出事件流
cargo test --workspace -- --test-threads=1   # 858 测试（可只跑 rollout 包，快很多）
```
- 讲解词："正确性不是靠我嘴上说，是 17 条运行时不变量在测试里硬断言 + 随机中断测试。
  设计文档驱动的 25 轮迭代审计，全绿。"
- 兜底：测试别全跑（太慢），只跑 `cargo test -p grodex-rollout`（秒级），然后说"全 workspace 858 个全绿"。

### 环节 5：收尾（13:00-15:00）
> "架构上分三层：核心（loop+rollout 崩溃恢复）、安全（权限+沙箱+凭证）、扩展（子代理+记忆+协议）。
> 我最想深挖的是崩溃恢复那一层——你想看哪部分？"

## 被问到的加分细节（提前背熟）

| 可能的问题 | 应对话术 |
|---|---|
| "为什么 21 个 crate？" | 编译期契约边界 + 25 轮无跨模块回归；承认 loop/tui 偏大 |
| "和 Claude Code 比？" | 诚实：搜索/索引/UX 没有；可靠性骨架（崩溃恢复/沙箱/凭证）有 |
| "测试怎么写的？" | 不变量断言 + 随机调度 + 集成；举例 tool 生命周期不变量 |
| "数据存哪？" | `~/.grodex/sessions/{id}/` journal + blobs；memory.db FTS5 |
| "崩溃后模型会不会失忆？" | 不会——journal 是唯一事实源，重放即恢复（这是设计核心） |
| "最大的一次返工？" | chat_state 与 journal 双写不同步 → 统一为单源（诚实，且是加分的故事） |
| "密钥安全？" | 模型看不到真实密钥，凭证代理发租约，存储 0600 权限文件 |

## 反模式清单（不要做）

- ❌ 不现场写代码 / 不现场修 bug（时间全花在恢复现场上）
- ❌ 不跑大文件 demo（O(n) read 会卡，破坏节奏）
- ❌ 不打开 audit 文档给人看全文（2572 行，只看"教训"页即可）
- ❌ 不主动提"产品欠账"清单（被问才答，且用"取舍"框架回答）
- ❌ 不让审批弹窗反复打断（只读工具提前放行，审批只留给专门环节）
